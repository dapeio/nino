# `/_admin` — The Workbench

This manual is about the one management interface of a Nino project: `/_admin`, the workbench. Developers set the project up and build its structure and appearance in it; editors maintain its content in it. What an account sees is what its permissions allow, and the screens explain themselves; what they cannot say is here - who may do what, how to get back in, and what to check when something does not work. The wizard that turns a fresh checkout into a project is the workbench's first-run mode and has its own reference, the [Setup Wizard](setup.md).

**Security Note:** Every panel writes directly to configuration and project files. A developer account can change routing, data models, templates and the visible website; an editor account can change content. Work from a current Git state or another reliable backup, use HTTPS only, and give every account exactly the role it needs.

## Login, Accounts and Roles

Open `https://your-domain.example/_admin` and sign in with the email address and password of your account. The first account is created by the wizard's **Accounts** step; every further one in the **Users** panel.

An account may carry a **name**, a field of the Users panel that is optional and holds one line of at most 60 characters - it is refused when it is longer or holds a control character, never cut. A feature that addresses the account does so by it, and the list of the panel shows it at the beginning of the second line of the account's row. It sits in the account's record in `config.php` as `name`, and only there when there is one. It is not written to the activity log.

There are no separate passwords for developer and editor work any more. An account holds a **role**, and a role is a named set of permissions, kept in `config.php` under `/nino/auth/roles`. The wizard writes two; the **User roles** tab of the Users panel changes them or adds more:

| Role | Permissions | Sees |
|---|---|---|
| **Editor** | every Content panel's permission, for the panels that exist when the wizard runs | the Content group, and its own profile under System |
| **Developer** | `/*` | everything |

A permission is one string per panel or tab; `/*` matches every path below it, so `/_admin/*` would also open every panel, and `/*` opens every panel of every future module as well.

An account that may manage users still stays within what it holds itself: it hands out no role and sets no password, and it renames, deactivates, deletes, logs out, unlocks or gives another role to no account - and it renames, empties or deletes no role - that holds a permission its own account does not. The Developer holds everything and so changes everything; the form of an account or a role beyond the signed-in one shows what it holds and offers nothing to press.

| Panel | Permission |
|---|---|
| Dashboard | none – every account |
| Elements | `/_admin/elements/manage` |
| Element Types (tab of Elements) | `/_admin/types/manage` |
| Text | `/_admin/text/manage` |
| Text Keys (tab of Text) | `/_admin/keys/manage` |
| Images | `/_admin/images/manage` |
| Image Slots (tab of Images) | `/_admin/slots/manage` |
| Favicon (tab of Images) | `/_admin/images/manage` - the permission of the Images panel |
| Submissions | `/_admin/submissions/view` |
| Log | `/_admin/logs/view` |
| Builder (the Builder feature) | `/_admin/builder/manage` |
| Routes | `/_admin/routes/manage` |
| Navigations | `/_admin/navs/manage` |
| Users (own profile) | none – every account |
| Users (other accounts), User roles (tab of Users) | `/_admin/users/manage` |
| Login protection (tab of Users) | `/_admin/lockout/manage` |
| Recovery password (tab of Users) | `/_admin/recoverypw/manage` |
| Language | `/_admin/language/manage` |
| Translations (tab of Language) | `/_admin/translations/manage` |
| Backups | `/_admin/backups/manage` |
| Config | `/_admin/config/manage` |
| Features | `/_admin/features/manage` |
| Maintenance | `/_admin/maintenance/manage` |

A feature's panel brings its permission along - the catalogue's Newsletter feature `/_admin/newsletter/manage`, its Forms feature `/_admin/forms/manage`, and so on - and the roles tab of the Users panel offers it while the feature is active.

Every action of a panel travels through `POST /_admin` with the name of the action in the field `action`, and two checks stand before it. The kernel checks the session token and that an account is signed in: a request with no valid token is refused with `403`, and a request with a token and without an account - no session, an ended or revoked one, a locked or deactivated account - is answered `401` with the code `session`, before the action is called. Every page of the site hands a token to whoever opens it, so the token says nothing about who sends the request, and no action of the workbench is open to a visitor. What the account may do is not the kernel's to say: the action checks the permission itself, with `\Nino\Admin\Admin::guardPerm()` as its first line, and answers `403` where the account lacks it. An action without that line is open to every signed-in account, an editor's included.

### Finer permissions inside a panel

The permissions above are doors: they say which panels an account may open. Inside Elements and Text, a role can also be described action by action and field by field – for editors who may change texts but not add entries, or who own one type and see the rest.

| What | Permission |
|---|---|
| Add an element of a type | `/_admin/elements/services/insert` |
| Change one field of it | `/_admin/elements/services/update/title` |
| Every field of it | `/_admin/elements/services/update/*` |
| Delete one | `/_admin/elements/services/delete` |
| Everything on that one type | `/_admin/elements/services/*` |
| Change one text key | `/_admin/text/update/template/page-home/hero/title` |
| Every key of a template | `/_admin/text/update/template/page-home/*` |
| The page details of a route | `/_admin/text/update/_nino/webpage/home/*` |

A whole page takes two of them - its template and its page details - because the details of a page, its name in the menu, its title and its description, are the system's keys under `/_nino`, not words of the template. These are ordinary permission strings, matched by the same `/*` rule as everything else, so a role is described as coarsely or as finely as it needs to be. The panel permission is still required: `/_admin/elements/manage` is what makes the panel appear at all, and the finer ones say what may be done in it.

**They are opt-in.** A role holding none of them keeps exactly what its panel permission has always meant – every action on every type and key. Giving a role its first finer permission for a panel is what says "describe this one in detail"; from then on that panel allows what the role names and nothing else. Existing roles are therefore unaffected until you change them.

The list of them is unbounded - it grows with every type, field and text key a project has - so the **User roles** tab does not offer it as one list: below the lists of ticks, in a section of its own, three lists that depend on each other pick one - **Area** (a type, a text group), **Action** (add, change, delete, or everything in the area) and, where the action has fields, **Field** (all fields, or one). **Add permission** ticks it in a list of its own under them, where a tick taken away takes the permission away; nothing is typed, so only what the panels list can be added. A field whose name has a space or an umlaut in it cannot be part of a permission and is not listed - it stays under its type's blanket. Adding the first finer permission of a panel asks first, because that panel then allows only what the role names, and so does removing the last one; a summary under the lists - *This role may …* - says in words what the role does. An account that does not hold the whole panel - it lacks the door, or is described in detail for it - cannot write a role, hand one out or set a password so that the set opens that panel with no finer permission - that would allow more than the account is allowed - and is told which panel it is.

What a role may not do, it is not offered: a field it may not change is shown read-only, "New element" and "Delete" disappear, and a text group it may not write anywhere loses its Save button. The refusal itself is server-side, so a request that goes around the screen is refused too.

A panel an account lacks the permission for is not rendered at all, and its actions answer `403` regardless; a pane shows only the tabs the account holds. A missing menu item or tab is therefore usually intentional, not a display error.

After five failed attempts, an account is locked for an hour – both numbers are the **Login protection** tab of the Users panel, which also lists the accounts locked right now and lifts a lock; the same counter runs per address, so guessing across accounts is throttled too - behind a reverse proxy that address is the proxy for everybody unless **Reverse proxies in front of this site** names it, and then one stranger's wrong guesses lock the whole site out. Accounts and roles live in `config.php`, the login throttle's counters in `private/data/auth-tries.php` – not in `config.php`, so a run of wrong guesses does not rewrite that file on every attempt; a counter below the threshold ends after the same hour as a lock, and the file keeps at most 5 000 entries - the oldest counters leave first, a running lock never.

For operation:

- use `/_admin` exclusively via HTTPS;
- create editor accounts with the **Editor** role and add a role only for a concrete need;
- keep the number of developer accounts small;
- sign out via **Logout** after work;
- additionally protect the path via web server, VPN or IP allowances if the hosting allows it.

If the accounts themselves are what is broken – the last developer password forgotten, a bad restore – the [recovery page](#recovery) is the way back in.

## Two Languages

The workbench has two languages, and nothing ties them together. The **interface language** is the one the screens, the rail and the messages are written in: the picker in the rail's settings menu sets it, so does the login page's, so does `?locale=xx` on the address, and it is kept for the session. The **working language** ("Edit content in") is the one the content is edited in: it is chosen once for the whole workbench, in the account area of the rail (folded, and on a phone, in the settings menu beside the interface language), only where the project has more than one language. Elements (the list of a type as well as an element's form, which writes the language on screen and no other; a text that the chosen language does not have yet shows the text of another language with that language's code beside it; the list sorts such a text as empty and the search finds it), Text and the Keys tab show it - their own selects say the same language and change it for all of them -, Routes names its pages in it where they have a name in it, and a view that shows it where it is not the native language of the project says so with a pill in its bar. It starts as the native language and is a value of the session of its own; changing it asks first where a form holds unsaved input, and draws the open view in the new language. Changing it changes what the panels show and open on and nothing else - the workbench goes on speaking the interface language after a reload, and the website in the same browser keeps the language its own visitor picker chose, since the workbench never writes that one. The Design preview of the catalogue draws the site as a visitor of this browser sees it, in the language the website shows them (`\Nino\Locales::getVisitorLocale()`), and the workbench stays in its own language; a Design that does not ask for it draws in the language the request is in, the interface language.

## Languages of the Website

A language is added under **Language**: **Add language** creates its text file, every key of the native language in it, all empty but for the language subtag (`fr` for `fr_FR`) the pages of the language say in their `lang` attribute and, where the Legal module is on, the names of its two pages; the language is not switched on. It is translated under **Text** first: the select above the texts lists every language that has a text file, and one the website does not serve yet is marked **Inactive**; the Keys tab and the Translations tab (a JSON document for a translator, imported into any language that has a file) work on it the same way, and an import never lets an empty value overwrite a text. Tick the language and save when it is ready. The select names the **working language**, so a new key made on the Keys tab starts with its value in the working language and empty in every other language of the site.

What a language does not have yet falls back to the **native language**, in the order the site lists its languages and then the other text files: a text that is missing or empty (whitespace is empty) is shown in the native language's words, on the pages of the site and in the mails alike, a post that exists in German only is listed on the English page in German, and the block that shows it on a page says so with a `lang` attribute. The **Dashboard** counts the texts that are empty in a language of the site while another language has one, the native language included, and each notice leads to the Text panel (it shows to an account that may use it). A feature that is switched on brings its words in every language the site serves - a language it has no words of gets the keys, empty - so the count and the fallback cover its texts as well, and an update of the kernel merges the words of the base unit once, at the first login after it (see [Updates and Rollback](deployment.md#updates-and-rollback)).

## Addresses

Every screen of the workbench has an address, the part after the `#`: `#users` is the Users panel, `#roles` its tab **User roles**. The address of a panel with tabs is the panel's own screen, its first tab - a link to the panel, an address typed by hand and the back link of a panel all open it there, whichever tab was open last - and the address of a tab opens that tab. The rail is the one way in that remembers: its links, and the select that stands in for it on a phone, open the tab that was open last in that panel until the page is loaded again, and the address then names that tab. What a panel shows deeper than its tab - an element, a text, an account - is written after the name (`#elements/<type>/<element>`), so that a reload, a copied link and the browser's Back and Forward return to it.

## Routes and Navigations

Both panels have an address for every view: `#routes` is the list of pages, `#routes/@new` the form of a new route, `#routes/<Element URI>` a route (the Element URI percent-encoded, `#routes/%2Fabout`) and `#routes/feature/<Element URI>` a page a feature or a module serves by itself; `#navs`, `#navs/@new` and `#navs/<key>` (the at sign is in no key and in no Element URI, so a navigation or a route called `new` has its own address) are the same for the navigations. A reload, a copied link and the browser's Back return to the view. A save leaves the person in the view it was made in and says so as a toast, a new route or navigation gets its address when it is saved, and only a delete goes back to the list.

A route has one address for every language or one for each (the switch **One address for every language**); the name, the title and the address of every language are one row each under one another, the working language first, and the description is the one of the working language - the other languages keep theirs, and a view that shows it in a language that is not the project's native one says so with the pill in its bar. The navigations a page stands in are the ticks of **Show in navigations**, each named by its name and, quietly behind it, its key. What the server refuses and names a field for - an address of one language, a name - is said under that field.

A navigation has a **name**, which is optional, beside its key: "Main menu" for `main`. The panels show the name first and the key quietly behind it, and a navigation without a name is shown by its key. The key is still what a template asks for with `[navigation nav="main"]`; the name is for the workbench alone. It is kept in the key `/nino/html/navnames` of `config.php`, a list of `key => name` of the navigations that have one, a key of its own - the first name written puts it at the end of the file - beside the plain list of keys in `/nino/html/navs`, which stays a list. The key is absent while no navigation has a name, so that a project that never names one keeps its `config.php` byte for byte. A file written by hand is read as it stands: an entry that is no text, or one for a key no navigation has, is read as no name and is never dropped when another navigation is saved; where the whole key is no list, no name can be saved until it is corrected. A name is one line of plain text of at most 80 characters, with no control character in it and no blank at its ends (`\Nino\Modules\Navigation\Admin::cleanName()`); renaming the key takes the name along, and deleting the navigation takes it away.

## Elements and Element Types

Every view of the two has an address: `#elements` is the list of types, `#elements/<type>` the elements of one, `#elements/<type>/<element>` one element and `#elements/<type>/@new` a new one; the tab has `#types`, `#types/<type>` and `#types/@new` (the at sign is in no element name and in no type, so an element or a type called `new` has its own address). A save leaves the person in the form and says so as a toast; a new element or type gets its address when it is created, and only a delete goes back to the list.

The list of types is a list of rows, each with the number of its elements; the elements of a type are a table with a search, its heads the words of its fields. The form of an element shows the working language and writes it: switching the language in the rail draws the form again in the other language, after asking what to do with what was typed, so that no field is ever written into a language it is not shown in. The one exception is the copy made by **Duplicate element**, which carries every language the original has and writes them all when it is created. A save sends only the fields that were changed - those every language shares as well as those of the language on screen - so a form saved without a change writes nothing and keeps the file byte for byte, a second window does not write back what the first changed in a field it never touched, and an element opened in a language it has no text in can be saved there, a required text of that language not asked for, until something is typed into that language. A type saved without a change writes nothing either. A yes or no is a switch, an image is the file field and uploads at once, a text of several lines and a rich text have the **[ ]** of the textfills where the account may edit the field and the server names it, and what is wrong - the server's refusals too - stands at the field.

The form of an element type has one card for each field: its name and its type, one group of ticks for the properties that are a yes or no, and the options of that type, each with its label at the left and its explanation behind a question mark; the buttons that move a field and take it away are icons. **Duplicate element type** is a dialog and takes the words the fields are called in the element form along, and **Delete element type** asks for the identifier of the type to be typed, naming what goes with it - the number of its elements and their pictures - and is shut while another type points at this one.

## The Mode

The workbench marks a project that is in **Development** with a chip in the warning colour at the end of the account block in the rail; a project in **Production**, the mode a live site is in, shows nothing. The chip is a link to the **Config** panel, where the mode is a select in a group of its own above the rest; an account without that panel sees the chip without the link, and a folded rail, like a screen narrower than 38 rem, keeps its first letter, the word being read out and the sentence of the mode its title. The mode is `/nino/mode` in `config.php`, `production` where the file does not name one.

Nothing in the kernel reads the mode while it runs. Switching it in the Config panel *writes* four settings, over what the form holds for them: **Development** shows errors on the page (`/nino/error/display`), logs them (`/nino/error/log`), switches the page cache off (`/nino/cache/status`) and gives it a lifetime of a minute (`/nino/cache/ttl`); **Production** hides the errors, logs them, switches the cache on and gives it an hour. Each of the four stays a field of its own that can be changed afterwards without changing the mode, and saving the mode as it is writes only what the form holds. The workbench's own log (`/nino/admin/logs`) is not part of it.

What the workbench reads the mode for is how much it asks. A question has one of three weights: *routine*, what is done all day; *big*, what reaches visitors or many records at once - renaming an element type, importing translations into the native language, a role's scope, deactivating an account or a feature, logging an account out everywhere, narrowing the format of a text key; and *destructive*, what cannot be taken back - deleting, removing a picture, restoring a backup. In **Development** only a destructive action asks. In **Production** all three ask, and a big one adds a line that the website is live and not in maintenance, unless the [maintenance page](#maintenance) is up. The weights and the rule are the shell's: how a panel asks is in the [panel recipe](recipes/admin-panel.md#saying-what-happened).

## The Head of the Dashboard

Above its notices the Dashboard has room for areas a feature brings - a card that greets the account, say. The kernel draws none of its own, and a project without such a feature opens the Dashboard on its notices and tiles.

A feature takes the place in two halves. Its script registers the area by a name, `Nino.admin.dashboard.head.add( name, render )`, where `render( data )` answers the element to draw, or `null` for none; the script of a panel of the feature does it, since the scripts of the panels are the ones the workbench loads, and it asks first whether `Nino.admin.dashboard.head` is there. The server half is a callback of `/nino/admin/dashboard/head` registered in the feature's `init()`: it is handed the areas so far, `name => data`, and answers them with its own. The Dashboard fires it once for each answer of its summary, for every account that opens the Dashboard, so a callback decides by itself what an account may see; an entry whose name is no lower-case slug (`/^[a-z][a-z0-9-]*$/`) or whose data is no array is named in a warning and left out, a callback that throws or answers no list is named and its answer dropped without taking the areas of the others, a name that is taken stays with the first, and the answer carries a `head` only where an entry is left. The areas stand in the order they were registered, above the notices, and an area whose name the answer does not carry is not drawn. What the server sent is the area's to set as text, never as markup. An area whose `render()` throws or answers something other than an element or `null` is named in the console and left out; the Dashboard is drawn without it.

## Unsaved Input

A form that holds input nobody has saved asks before it is left, and every way out asks the same question - **Save**, **Discard** or **Cancel**: the back link of the form, a move through the rail (its links, and the select that stands in for it on a phone), the interface language, a log out. **Cancel** stays where you are and puts the rail back as it was - the open link, the select and the address - and **Discard** forgets the input and leaves the form: one with a Back link is left the way that link leaves it, and is drawn again from what is stored when it is opened next; one that is the whole screen of its panel shows what is stored again. What was left behind is a clean form and not one with input nobody will find again. A move from one tab of a pane to another leaves nothing and asks nothing. The one exit that is not the workbench's is a reload or a closed tab: the browser asks that itself. **Ctrl+S** (**Cmd+S** on a Mac) saves what is on screen where it holds unsaved input, as the Save button of the form does; the browser's own answer to the key, saving the page to disk, is taken away in the workbench.

## Following the website

**Website window**, an icon in the rail's account block beside the icon of **Log out** - each is named by its label for a screen reader, and the title of the window says what it does - opens `/_admin/?follow` in a window of its own: a bar and the website below it in a frame. It is made to stand beside the workbench - on a second monitor, or next to the browser window of the workbench - and to show the website as it is after every save. A second click on the link opens the same window again, at the page it showed last, and the browser brings it forward where it lets a page do so.

Whenever a panel writes something, the window loads the website anew; several writes within a fifth of a second are one load, since a save often touches two kinds of data. A panel that knows which page it wrote - Routes does, for the page it saved - names it, and the window goes there. The switch **Follow the page** in the bar decides what a name does: on, the frame goes to the page that was saved, and off, it loads again the page it shows, which is what you want when you work on one page and save another. The switch is kept in the browser, on to begin with. **Reload** loads the frame anew at once, and the bar shows the path of the page the frame is on. `/_admin/?follow&uri=/blog` opens it at a page of the website and wins over the page it showed last, which a window opened without an address remembers in the browser; anything that is not a path of this site - an address with a host, a control character, or the workbench's own `/_admin` - opens the home page. The window is a query of the workbench's own address and no path of its own, because that address is the one every server setup, whatever it forwards to the site's `index.php`, reaches the workbench by.

The window and the workbench talk through the browser (a `BroadcastChannel`), so they have to be in the same browser, on the same address of the site; a window in another browser or another profile is not told, and **Reload** is its way. The window needs an account like the workbench does, and a signed-in account is never answered from the page cache: the frame shows what the files hold now.

## The Manual: the ?

Every pane ends its head with a **?**, a button that opens the manual of the panel in a dialog: what the panel is for in a sentence, then one entry for each thing done in it. The manual of a panel of the workbench is written for the people who work with it, in both languages; the manual of a feature's panel is the one its manifest carries, which the Features panel shows to the people who develop with the feature (a feature that says nothing about its use has no **?**). The Dashboard, which has no head to put it in, has the **?** in a row of its own. Escape or the button at the foot closes the dialog and the focus goes back to the **?**. How a panel brings one is in the [panel recipe](recipes/admin-panel.md#the-manual).

## Features

**Features**, a panel of the System group, switches the packages of `features/` on and off, sets them up and installs them from a catalogue; how one is written is the [feature manual](features.md). The setup wizard offers none by itself: a feature is switched on here, or comes with an application the wizard's [Application step](setup.md#5-application) places.

### The panel

The panel asks for `/_admin/features/manage` on every action, a developer's permission. It sorts every directory below `features/` that carries a valid manifest into three tabs - **Active**, **Inactive** and **Available** - and offers the applications of the catalogue in a fourth, **Applications**; each has its count as the chip of its tab, Active first, and each is the same table of the workbench: a search over its full width (name, key, description, category), the columns name, category, version and state, and the small buttons of a row at its end, the one that takes something away last and in red. A category select in the head of the panel narrows the first three at once - an application has no category, so the select is not drawn on the fourth. A row of a feature opens the view of that feature, which has an address of its own, `#features/<key>`, that survives a reload; a key the project does not have is an empty state with the way back. A row shows name and description in the interface language - they come from the manifest, because the texts of a feature that is off are not loaded - the version, the category, and whatever stands in the way of an activation: a Nino version the feature was not written for, a PHP extension that is missing, a required feature that is not in the directory. A directory whose manifest the kernel refuses - one that breaks a rule, does not parse or throws when it is read - is not a feature to the kernel. The **Inactive** tab lists it all the same, by directory name, with the reason the log holds (the kernel's English sentence), written as text and without actions, so that a feature does not vanish without a word. One whose class is still listed in the modules, a feature that was on when its manifest broke, stands under **Active** instead, with the sentence that it runs incomplete: its `init()` runs and its panel is in the menu, and a backup stops while it is so (see [Backups and Restoration](deployment.md#backups-and-restoration)). Its row has one button, **Deactivate**, which asks first and then takes the class out of `/nino/modules` (`features/deactivate-refused`, by the name of the directory, and only for one that is listed as running): the feature then stands under **Inactive** with the reason, and the backup runs again. What a switch-off otherwise reads from the manifest cannot run for a manifest nobody can read - whether another feature requires it, where its shortcodes stay in pages, which sections of the privacy policy still describe it - and the question says so; nothing is deleted. Mending `feature.php` is the other way out.

The sixteen actions behind it are `features/list`, `features/activate`, `features/deactivate`, `features/deactivate-refused`, `features/reapply`, `features/settings`, `features/remove`, `features/catalogue`, `features/install`, `features/application-plan`, `features/application-apply` and, for the themes and packages of blocks of the catalogue, which the panels of the features that use them show, `features/catalogue-offers`, `features/package-install`, `features/package-update`, `features/package-remove` and `features/package-preview` (see [Themes and packages of blocks](#themes-and-packages-of-blocks)); behind the first seven stand `\Nino\Features::all()`, `activate()`, `deactivate()`, `deactivateRefused()`, `activate()` once more, `saveSettings()` and `remove()`, behind the next two `\Nino\Catalogue::fetch()` and `install()`, behind the next two `\Nino\Applications`, behind the last five `\Nino\Catalogue` and `\Nino\Packages`. What an action says about what it did is a toast, and what stays to be read - the places that still hold the shortcodes of a feature that was switched off - is a notice at the top of the list, never a dialog of the browser: the workbench is built again after a switch, so both are kept in the session for the page that follows - and only for that page: it is dropped for another account or after two minutes - which also opens on the tab the action was pressed on (`#features/@inactive`, `#features/@available`, `#features/@applications`; Active is the bare `#features`, and the @ keeps a feature that is called `active` or `inactive` at its own address `#features/<key>`), with the filters it had and the focus on the row that took the place of the one that left:

- **Activate** switches a feature on: the features it requires first, then its install unit, applied without overwriting anything your project has, the class listed in `/nino/modules` and the version recorded under `/nino/features`. The toast says that the feature is active, and names what was switched on with it, once the workbench has reloaded. Before it, the question of the workbench's modes lists the requirements that are off and come on with it; while it runs, the row says so and holds its buttons, and a refusal stands in that row.
- **Update** is offered for an active feature whose manifest names another version than the recorded one, after its directory was replaced with a new release. It is the same action: the unit adds what is new and the feature migrates its own data.
- **Apply content again** is in the bar of the view of an active feature that brings an install unit, beside Deactivate, asks first, and does what an activation does with the unit and nothing more: what the project lacks - routes, files, templates, element types, picture places, texts - is placed, deleted things included, and what it has stays as it is, a template or a text it changed included. Elements are content: those of a type the project has are not brought back, nor are deleted sections of the privacy policy; a type it lacks comes with its elements. The answer says for each kind how many were placed and how many were there already, which is how to see that a deleted copy came back. It is meant for the developer of a feature, whose changes to the unit reach a project only by a new version otherwise; to get a fresh copy of a template the project already has, delete the copy in the project (the template file under `private/templates/`, or the text in **Text Keys**) and apply the content again. It switches nothing on and updates nothing: it is refused (`features_reapply_inactive`, `_unit`, `_update`, `_problems`, `_requires`) for a feature that is off, one without a unit, one with an update waiting - the update applies the unit together with the migration of its new version - one that cannot run here, and one whose requirement is off, waits for an update or cannot run; the button is not drawn for those. It changes neither the module list nor the recorded version.
- **Deactivate** removes the class from the list and nothing else - settings, data and copied templates stay, and activating again finds everything as it was. It is refused while another active feature requires this one. A notice at the top of the list then lists the places that still contain the feature's shortcodes and components (templates, texts, elements), because a shortcode of a feature that is off stays the text it is written as and a component is a name nobody has registered; which are the feature's is read from what is registered (`\Nino\Features::shortcodes()`, `\Nino\Features::components()`), opening tags in raw brackets only - one the Text panel stored as `&#91;...&#93;` was never rendered and is not reported; the panel changes nothing there. Before the switch it asks, naming what stays - the shortcodes, the sections of the privacy policy and what the feature installed - and, for a feature that brings components, the templates that call them, up to ten and the number of the rest (the list of the panel carries them as `calledIn`), since a page made of them draws nothing while the feature is off; declining does nothing. The notice also names the sections of the privacy policy that still describe the feature - the Dashboard keeps saying so while the feature stays installed - and an editor hides them under **Elements › Privacy policy** if they no longer apply. There is no uninstall, deliberately: deleting a file the project may have edited in the meantime would not be safe, and what a feature leaves behind, a developer removes knowingly and by hand.
- **A feature that comes with Nino**, the feature **Basis**, is in the list with the label *Comes with Nino* and is switched on and off like the others: it brings the components the starter pages are written in ([the feature Basis](features.md#the-feature-basis)). It has no directory of the project's to remove and no version of its own to update - it is updated with Nino - and the settings screen of a feature that is on names, in red, each component of its folders that Nino did not register and why (a schema that is refused, a group another feature has claimed); the feature runs without that component, and the line keeps nothing from being switched on.
- **Uninstall** deletes the directory of an inactive feature, the one step deactivating leaves out, and says what it takes and what it keeps in the question before it. What the feature kept stays, so putting it back finds its settings; an active feature is refused, since a directory deleted from under the autoloader is a fatal on the next request.
- **Applications** lists the applications of the catalogue this project reads - the one under `/nino/catalogue/url`, believed with `/nino/catalogue/key` (see [the catalogue](#the-catalogue)); the cache fills the tab and **Refresh catalogue** loads it - each with its name and description, the features it switches on and a word that says how far it is set up: *Set up* when every feature of it is on, *Partly set up* when some are (the ones still off are named) and *Not set up*. That is read from the features on disk every time: an application is no state that is stored, and a feature switched off singly takes it back to partly set up. **Set up** first asks the server what it comes to (`features/application-plan`): what loading needs - `openssl`, `Phar` and `zlib`, `curl` or `allow_url_fopen`, a writable `features/` - is named in the interface language before anything is loaded, the signed index is read again, and the features that are off are listed in the order the application gives them. Then it asks, as a deactivation does - in the workbench's mode, so a project in production is told the site is live - naming what is about to be loaded and switched on, and that no page, route or start page is changed. Each feature then goes in a request of its own (`features/application-apply`), so the card shows which is under way: placed below `features/` where it is not there, switched on where it is not on, with what it requires - the one step the setup wizard takes as well, `\Nino\Applications::place()`, and a feature that is on is left as it is, and one that is on with an update waiting gets the update, which the card names apart from a feature that is off. Where one fails the run stops: the row names the feature, the reason and which features are on, what is on stays on, and **Try again** goes on from there. After the last a toast names what was switched on and the workbench reloads on the Applications tab (`#features/@applications`); an application that has a `next` then links to it, *Set up <name>*, a path of the project that the server has checked as the wizard does. Only a key the catalogue lists as an application for this Nino and a feature of that application are accepted; any other key is a 400 before any archive is downloaded - a malformed key before the catalogue is asked at all, a well formed one after the signed index and its signature are read - and a catalogue that is off, cannot be read or is not signed with the configured key is refused with nothing placed. An application is set up without touching the project's pages: no starter page is created and no route is changed or removed - what changes in `config.php` is the module list, the record of the features and what the install units of those features add without overwriting. An application that says `start: own` leaves the project's start page where it is, and its feature offers its own page itself; applications that say who provides the start page can be set up side by side, which only the wizard rules out.
- **One change at a time.** Placing a directory, switching on, switching off, removing, applying an update, saving settings and setting an application up run under one lock of the house (`\Nino\Features::lock()`, a side-car file in `data/.locks`, the kind `Filesystem::lockFile()` makes); so does the wizard's Languages and modules step once a feature is on. Between the look at the directory and the write to `config.php` no other change slips in, from another session or another request, so a feature is listed in `/nino/modules` only while its directory is there, and a directory that is gone is not listed. The lock is not waited for: a change that finds it taken answers 409 with the code `features_busy` (`install_busy` in the setup wizard) and has done nothing, and asking a moment later goes through. A lock file that cannot be opened at all - another owner, a directory in its place, a `data/.locks` the web server may not write - is not busy: it answers 500 with the code `features_lock_failed` (`install_lock`), and the log says which file. Whatever a change writes to `config.php`, it reads from `config.php` when it holds the lock: the module list and the record of the versions are read, changed for the one feature and written on the file, never the copy the request booted with. A module that the request lists and the file does not is not kept - it was taken out meanwhile, or only this request registered it - and nothing of the sort is written back. The lock goes with the process that holds it, however that ends; the pages of the site never take it.
- **What an answer says about the server.** A refusal that comes from php, the archive or the filesystem - an archive that is no archive, a directory that cannot be written or removed, a download that fails on a file of the server - is a sentence without a path: the answer names the feature and, for an archive, the name of an entry in it, but never a directory of the project or of the temp directory. The full text, path included, goes to the log of the house (`/nino/error/log`); with `/nino/error/display` switched on, which is for development, php shows the warnings of the log in the answer as it does anywhere else. Every refusal of these actions carries a code with a sentence in both interface languages (`features_unknown`, `features_invalid`, `features_remove_active`, `features_install_failed`, `features_install_inactive`, `features_activate_failed`, `features_deactivate_failed`, `features_remove_failed`, `features_application_failed` and the codes above), and the reason the kernel gave is the one parameter of its sentence.
- **Settings** are on the screen an active feature's row opens, in two tabs: **Description**, the sentence the manifest describes the feature with and under it its manual, and **Settings**, the form the manifest describes. Both tabs are built at once, so what was typed into a setting survives a look at the Description, and the one Save collects the whole form whichever tab is on; every setting is validated before any is written, an error names the setting, and the values are stored under `/nino/features` in `config.php`. A feature that declares no setting has the one tab it has and no strip over it. A feature that has a panel of its own and settings gets them there instead, as a **Settings** tab of that panel on the same actions and the same permission, and its screen here links to that tab - an account that holds only the feature's own permission does not see them, and an account that holds only `/_admin/features/manage` gets that panel in its rail, opened on the Settings tab alone.

A panel a feature brings appears with the next load of the workbench after the activation and goes with the next one after the deactivation; the panel reloads the workbench itself. It lands in the rail's **Features** group whatever its own `nav()` names and offers its permission on the roles tab of the Users panel under that group's label - the **Editor** role the wizard wrote does not receive it by itself, grant it there.

### The catalogue

A feature, a theme or a package of blocks that is not copied in by hand comes from a catalogue: a `catalogue.json` published over https beside the archives it lists, and a detached signature `catalogue.json.sig`. Nino's own is `https://catalogue.getnino.dev/catalogue.json`, built and signed by [dapeio/nino-features](https://github.com/dapeio/nino-features); the kernel side is `\Nino\Catalogue` and the one http client `\Nino\Fetch`, both checked without a network by `tests/catalogue-smoke.php`.

The **Available** tab shows what the catalogue offers that this installation does not already have current. Only **Refresh catalogue** fetches: the tab fills from the cache, `data/catalogue.php` (when it was fetched, under which url, the parsed document - ignored when another url is configured now), a status line says when it was last read, and the offers are matched against the features on disk every time. Loaded, it offers **Install** for a feature that is not in the directory, **Update** for one there in an older version, and greys out, with what it asks for, one no version of which fits.

Install downloads the archive, checks it against the signed catalogue and puts the directory in place; then it switches the feature on in two of three cases. A feature the project did not have is switched on - pressing Install says the project wants it. An active one is activated again, which applies the update in a second request the panel makes on its own, since the first booted with the previous version's class. One that is there and switched off stays off: a newer version of it is not somebody changing their mind. Requirements come along: the whole set is worked out first, checked against this kernel and placed deepest first, so the feature asked for arrives last; one already on disk stays as it is, whatever its version, and one the catalogue cannot serve refuses the install with nothing placed. A toast names what came along; where the files are placed but the activation fails, the panel says exactly that. Where `features/` is not writable, the tab links the archive instead, to unpack by hand.

The signature is the trust: ECDSA (P-256) over SHA-256 of the exact bytes of the document, DER and base64 (`openssl dgst -sha256 -sign key.pem catalogue.json | base64`), checked against `\Nino\Catalogue::PUBLIC_KEY`, or against the PEM in `/nino/catalogue/key` for a catalogue of your own, found at `/nino/catalogue/url`; an empty key falls back to Nino's, and a url of `''` switches the catalogue off - the tab says so, there is no Refresh button and no request. An installation fetches the catalogue again rather than trusting what the panel showed, downloads the archive within the byte cap of its entry, refuses one whose size or SHA-256 differs, reads it in memory with `\Nino\Archive` (one folder, plain files and folders only, nothing outside it, no link, a depth and a count and a size that are bounded - nothing is written before all of it is looked at), has `\Nino\Packages` check what a feature, a theme or a package of blocks may be and require the key and version the catalogue promised - a feature by its manifest, which is read from the staging folder below `data/.packages/` before the exchange -, and only then exchanges the folder, putting the old one back if that fails.

It needs the `curl` extension or `allow_url_fopen`, `openssl`, `zlib` and a writable `features/`. Every request goes over https to the catalogue's host and nowhere else - no redirect followed, the certificate verified, the user agent `Nino` and nothing more, and the host of the index, of an archive and of a picture is a name of the public internet (`\Nino\Fetch::isPublic()`: no address in place of a name, no ending of a local network, no address among the ones the name has that is not global - private, loopback, link local, shared, documentation, benchmark, multicast, site local, 6to4, a local NAT64 - and the request goes to the addresses that were checked, not to what the name answers a moment later; a server that cannot resolve the name says so) - and only when someone presses **Refresh catalogue**, **Install** or **Set up**, or reaches the wizard's Application step: no check in the background, no telemetry, nothing sent. A directory copied into `features/` is a feature like any other.

The index may also list **applications**: a few named sets of features with a place to continue in (`next`, a path of the project), a statement who provides the start page (`start`: `starter`, `own` or nothing) and, where the workbench is to open on the entry point with its menu folded, `menu: folded` - *Website*, *Blog*, later others, each one worth having only as a whole. The kernel reads them with `Catalogue::parse()` (an application of the wrong shape is dropped, the rest stays; an index without the key has none) and offers those whose features all fit this Nino with `Catalogue::applications()`. They are offered by the setup wizard, from the official catalogue only ([Applications](setup.md#5-application)), and later by the Features panel's Applications tab, from the catalogue the project reads: the wizard knows nobody's address and key but the kernel's, the panel the ones `config.php` names. Both place and switch on the features with the same code (`\Nino\Applications`) and believe a catalogue only with its signature.

#### Themes and packages of blocks

The catalogue lists three kinds of package. A **feature** goes below `features/` and is the code the rest of this chapter is about. A **theme** and a **package of blocks** are data without code: they go below `private/packages/themes/<key>/` and `private/packages/blocks/<key>/`, which no web server serves and no reader includes a file of, and a site hangs on neither - a theme that is applied is kept as a copy of the parts it uses, a block that is put in a page is the page's. What a package may hold is a list of paths that [`\Nino\Packages`](features.md#packages) checks while it is still bytes; a theme with a php file, an `@import` or a token of another group is refused as a whole, with the file and the rule, and nothing of it is written.

There is no screen of its own for them: the panel of the feature that uses a kind offers it - the themes in the panel of the themes, the packages of blocks in the Builder - and shows what the kernel answers. The five actions are the Features panel's, each behind `/_admin/features/manage` whatever panel posts it, and a change that finds the lock of the features taken is a 409, `features_busy`, as everywhere:

| Action | Posts | Answers |
| --- | --- | --- |
| `features/catalogue-offers` | `kind` (`feature`, `theme` or `blocks`), `refresh` (`true` fetches the catalogue, else the one kept is read) | `{ kind, catalogue: null }` where none is kept, else `{ kind, catalogue, catalogueUrl, fetched, writable, offers, unreadable }`: an offer has `key`, `name`, `description`, `version`, `nino`, `ext`, `requires`, `released`, `size`, `state` (`available`, `current`, `upgrade`, `incompatible`), `local`, `needs` (`features` and `fonts` that are not there, which a panel says as a hint: the features come with the package, a font does not), `blocked` (the features that cannot be had), `preview` (whether there is a picture) and `blocks`, of a theme `fonts` and `parts` too; `unreadable` lists the entries of the kind that were left out, `{ key, reason }` |
| `features/package-install` | `kind` (`theme` or `blocks`), `key`, `version` | `{ package, placed, switchedOn }`: the offer as the list shows it now, what was placed in the order it was (`{ kind, key, version }`, the features it asks for first) and the features that are on now and were not, which the install switches on as the install of a feature does. A package that is there is `features_package_installed` |
| `features/package-update` | the same | the same; a package that is not there is `features_package_absent` |
| `features/package-remove` | `kind`, `key` | `{ removed, kind }` - what uses the package is no reason to keep it |
| `features/package-preview` | `kind`, `key` | the picture as a file: webp, `Cache-Control: private`; fetched on the first request and kept below `data/.catalogue/previews/` by its digest - the catalogue lists the picture but does not load it, and the browser never asks the catalogue's host |

What the signed catalogue says is believed as far as the signature goes, and two things follow from that which are the catalogue's to answer for and are not checked by the kernel: an update to a version that is older than the one installed is made when the catalogue lists that version and the request names it (the list offers only the newest that fits), and a feature whose `directory` is the folder of another installed feature replaces that folder. The picture is answered inline as `preview.webp`; a picture that cannot be fetched is a 400 with `features_preview_failed`.

A refusal is a 400 with the code `features_package_failed` and the sentence of the kernel as its parameter - for a package with a file that may not be there, the path and the rule, as `\Nino\Packages::why()` says them.

#### A catalogue of your own

A catalogue is an address, a key and a directory of packages; `bin/build.php` of the [catalogue repository](https://github.com/dapeio/nino-features) publishes the `catalogue.json`, its signature and one `.tar.gz` per package. The document (format 2) holds `format` (`2`), `generated`, `packages` - one entry per published version, each with a `kind` - and optionally `applications`; a document of another format is refused as a whole (a catalogue of format 1 says so, and lists nothing), and so is one that is not signed. An entry that is wrong in a field costs that entry and nothing else - `\Nino\Catalogue::parse()` keeps what it left out with the reason, and a panel says it - and an entry of a kind this kernel does not know is skipped, so that a later catalogue with a new kind is read.

| Field | Kind | Meaning |
| --- | --- | --- |
| `kind` | all | `feature`, `theme` or `blocks` |
| `key`, `name`, `description`, `version`, `released` | all | what the manifest of a feature says, see [the manifest](features.md#the-manifest); the key of a theme and of a package of blocks is a slug of at most 40 characters |
| `requires` | all | an object: `nino` (the constraint), `php` (extensions) and `features` (keys; a theme and a package of blocks ask for the features their parts and components belong to, and they are installed with it); of a theme `fonts` too (slugs of the font repository: a hint, never installed with it) |
| `category`, `maturity` | feature | optional, the same two the manifest has; a reader drops one it cannot use without leaving the entry out |
| `directory` | feature | the directory the archive holds - `Newsletter`, the feature's class name segment |
| `parts` | theme | per group `{ feature, contract }`, which the panel shows without loading the theme |
| `blocks` | theme, blocks | the blocks of the package: a key, or `{ key, category }` |
| `preview` | theme, blocks (required), feature (optional) | `{ url, sha256, size }` of a webp picture of at most 256 KB, https |
| `archive` | all | the https url of the `.tar.gz` |
| `sha256`, `size` | all | the digest and the byte length of exactly that file: at most 8 MB for a feature, 2 MB for a theme and for a package of blocks |

An archive is a `.tar.gz` of exactly one folder: for a feature the directory that lands below `features/`, for a theme and a package of blocks the folder of its key, and nothing beside it; a feature's `tests/` are not published. It holds no link, no path with a `..` or a name that is none, at most six levels below the folder, and no name twice in another spelling.

## Maintenance

**Maintenance**, a panel of the System group, is one switch: while it is on, every visitor who is not signed in to the workbench gets a 503 answer instead of the site - the page itself and a module endpoint such as the contact form's `/.form` alike - and a signed-in account sees the site as it is, with a banner. `/_admin` and its login keep working throughout, so switching it off never depends on the switch itself.

The page a visitor gets is the project's own `templates/page-maintenance.tpl` where it has one - copied in by hand from the module's own `install/` directory, with `/module/maintenance/page/title` and `/module/maintenance/page/text` as its two texts, from then on editable in the Text panel like any other key - and otherwise the module's plain page in the site's native language, so the switch works from the moment the module exists. Nothing in the setup wizard installs the styled version on its own.

## Recovery

`/_admin/recovery.php` is the way back in when the accounts themselves are what is broken: every developer password forgotten, or a restore gone wrong. It asks for the **recovery password** set in the wizard's last step – not a login; the workbench asks for it in one place only, the **Recovery password** tab of Users, which changes it – and offers three things:

- **Restore a backup**, from the list of dates or from a file, after snapshotting the current state. It is the restore of the Backups panel, so what an archive holds - the templates in the folders of `templates/` among it - and what a restore refuses are the ones described under [Backups and Restoration](deployment.md#backups-and-restoration). It is also the one place where the **recovery key** of an archive of another project is typed - the key the setup wizard showed once when that project was installed - together with the archive as a file, in one request that keeps nothing of either; an archive opened with a typed key is accepted only when it holds data and pictures and no code (the same section has the steps, the limits and the rule);
- **Set a password** for an account that exists, picked from a list: it gets the new password, is logged out everywhere, and is unlocked and activated again if it was locked or deactivated - so a recovered developer account gets in. A typo cannot name an account, there is none to name;
- **Create a full-access account** - for when no account is left. It is its own action, asks to confirm before anything is written, and refuses an address that already has an account.

The page is written for the day nothing else works, so it asks nothing of the project: it speaks German or English, German first, from one fixed table of its own (`_admin/assets/recovery-text.js`) - the choice stands at the top right, is kept in the browser alone and is the one the wizard keeps - and it draws its forms with the blocks of the workbench (`Nino.admin.js`, a static file of the kernel). A question - a restore, an account with full access - is the dialog of the workbench, never the browser's; what is wrong is said under the field it is about, and the page says what the server refused in the chosen language, by the code of the refusal.

Each of the three leaves one line in the activity log, with `recovery.php` as the one who did it - nobody is signed in here - and never a password; a reset or a create the page refused leaves none, a reset that set the password and then failed to lift the lock leaves its line, a restore that failed leaves its line marked as failed.

Five wrong attempts lock it for an hour, the wrong current passwords typed into the Recovery password tab among them. The secret's hash lives in `private/.auth/pw.php` – outside `config.php`, so a restore cannot roll it back, and outside every tool directory, so an update cannot take it along. Only the wizard's last step and the Recovery password tab write that file. A secret that is forgotten, so that the tab has no current password to ask for, is written by hand - it is a php stub that refuses to be served, with the hash inside it:

```bash
php -r 'echo "<?php http_response_code(403); exit; return \x27", password_hash( $argv[1], PASSWORD_DEFAULT ), "\x27;\n";' -- '<password>' > private/.auth/pw.php
```

Do this in a protected local environment only – a password on a command line may be visible in the shell history or the process list.

The **Recovery password** tab of the Users panel changes the recovery password: the current one, the new one - at least eight characters - and the new one again. A wrong current password counts against the same five attempts `recovery.php` has. The tab cannot set a first password: where `private/.auth/pw.php` is missing, the one-liner above writes it. The tab needs `/_admin/recoverypw/manage`, a permission of its own that the Developer role holds through full access and the Editor role does not - whoever holds it can lock `recovery.php`, and with the recovery password restore a backup over the whole project.

## Text and Text Keys

Both tabs of the **Text** panel list the keys in groups - the pages first, then the project, the common words, the building blocks, the modules, the features and the system - with the list of the workbench, and a group has one name in both: a page is named by its routes in the working language, else by the name its template gives itself, else by its category as the vocabulary reads it ("Home", not "Page home"). Every group has an address, `#text/<group>` and `#keys/<group>`, and so has every key in it (`#text/template/page-home/hero/title`); the Text Keys tab has three more - `#keys/@new`, `#keys/@rename/<key>` and `#keys/@scan` - whose at sign keeps them from a group of the same name. The search is one box with a chip: *Empty in <language>* in the Text tab, *Hidden only* in the other. A hit is a row of the same list, the words found marked in its second line and the key small behind them.

Neither tab has a switch of the language. The texts are shown and written in the working language of the workbench; a group that is open shows one language, writes that one and no other, and says so with the pill in its bar where it is not the native language. A change of the working language with unsaved input asks first, and then the group is drawn again in the new language. A text of one line - plain, no line break in any language, no longer than a line, a limit of a line - is a field of one line; any other plain text is a field of several lines and a text with markup is the rich-text editor, and at those two the **[ ]** of the textfills stands at the name, for the account that may change the field. The list it opens is the answer of `text/fills` (`keys/fills` in the Text Keys tab), asked under the permission of its panel for the language the form is drawn in: the form posts it as `locale`, which is checked against the languages of the site and is the language of the session where it is none of them, so each fill says what it reads in the text of that language. A text that the account may not write is shown as text; one with markup is shown as the words it holds, not drawn as markup.

A group is saved with the one **Save** of its bar and the view stays as it is. Only what was changed is written, in the language the form was drawn in, so that a group saved without a change leaves the text files and `meta.php` byte for byte as they were; what a text is on screen is the text stored, and a toast says it. A key the server turns down is said at its field, stays marked as unsaved and is the only one that is: the others are saved. In the Text tab a field that is typed into while its request runs is unsaved input again when the answer comes; the Text Keys tab holds its controls while its requests run.

The Text Keys tab saves more with it. Every key has a row under its text - its format, its limit, whether it is global and whether it is hidden from the Text panel - and the small buttons **Rename** and **Delete** at the end of it. The shape of every key whose shape was changed is written by `keys/save` one after the other, then the changed texts by `keys/savebatch`, and then the keys are read again and the group is drawn from what the server holds; a part that was turned down - a limit under the text a key holds, a format - is said under its field and drawn again as it was typed, and the text of that key is not sent. A format that holds less than the one it replaces and a key that is made global ask once, with the heaviest weight, for all the keys they change, naming each: what is stored is converted and cannot be converted back, and a global key keeps the text of the native language and drops the texts of the others, which the line of the key names. A limit lowered under the text of a key and that text made shorter in the same save work together: the text is written before the new limit. After every drawing of the group the focus is on the main button, on the first field that was turned down, or, after a delete, on the field of the key that stands where the deleted one did. Where the keys cannot be read again after what was written, the form stays as it is, the line says that it was saved and not read again, what was turned down stays in its fields as unsaved input, and **Reload** reads them anew. A key is made and renamed in a view of its own: the four segments of `/<namespace>/<category>/<part>/<name>`, each checked when the form is sent - a segment that is not a word of a key is said under it, one that is not a word of the vocabulary is said as the name it will read as - and after it is made the group that holds it is open at the key. The namespaces of a template, a feature or a module stay behind a switch, for a key that unit does not bring.

## Images and Image Slots

The **Images** panel lists the categories of the image slots - the namespace and category of a slot that follows the text-key grammar, the first segment of any other - and opens one at its own address, `#images/<category>`. Every slot is a card: its target size, the pages that show it (or a notice that none does, so an image there never appears on the website), the call a template writes, the picture with **Remove image**, a file field and the alt text. Nothing is saved with a button. A file that is chosen is checked against the limits of the upload - the extension, the byte limit and the megapixels - and sent at once; the answer is a toast, a picture smaller than the target stays marked as scaled up, and what the server refuses stands at the field. An alt text is one short value for each language, the working language first, and is saved when its field is left and its value has changed, one language by itself; a failed save leaves the value in the field with its sentence, and the shell asks before a view is left with such a value.

The **Image Slots** tab lists the slots - `#slots`, with a row for each at `#slots/<the segments of its uri>`, `#slots/new` for a new slot and `#slots/scan` for the scan of the templates. A slot is made and changed in a form with its bar - **Delete image slot** at the left, one main button at the right - that stays after a save; its uri is fixed once the slot exists. What is wrong is said under the field, and a delete asks first.

## The Favicon Set (a tab of Images)

The **Favicon** tab of the Images panel makes the icons of the website from one picture. It shows the set as it stands - 16, 32, 180 (the touch icon), 192 and 512 pixels, the `.ico` and the vector icon where there is one - with the date of its files, and a form that takes:

- **Source picture** (**Quellbild**), a PNG, WebP or JPG of at least 512 × 512 pixels, within the limits the form names next to the field (the byte and megapixel limits of every upload). A picture that is not square is set whole in the middle of a transparent square, not cut; the pictures of the icons keep the transparency of the source. A GIF is not taken.
- **SVG** (optional), a vector icon for browsers that draw one. It is not converted: the file is read and rebuilt from the shapes it holds - paths, circles, rectangles, lines, polygons, groups, gradients and clip paths with their plain attributes - so that a script, a style, a foreign object, an embedded picture, a link, an event attribute, an external reference, a document type and an entity declaration are not in what is kept. A file that cannot be read as a plain vector picture, or has no shape in it, is refused with a message and changes nothing.
- **Background** (**Hintergrund**), a colour field - the hex code like `#1a2b3c` (three or six digits) with the picker beside it; a code that is none is said at the field and the set is not made. The touch icon (`apple-touch-icon.png`, 180 × 180) is drawn on a surface of this colour without an alpha channel and with a tenth of its edge left free around the picture - white where the field is empty. The icons of 16, 32, 192 and 512 pixels stay transparent. A colour typed here is also the `background_color` of the web manifest.
- **Theme colour** (**Themenfarbe**), a colour field for the `theme_color` of the manifest, the colour of the browser bar of a phone. Empty leaves the value the manifest holds.

**Generate** (**Erzeugen**) writes `favicon-16x16.png`, `favicon-32x32.png`, `favicon-192x192.png`, `favicon-512x512.png`, `apple-touch-icon.png`, `favicon.ico` (a container with three PNG pictures of 16, 32 and 48 pixels) and `site.webmanifest` to `public/favicon/`, and `favicon.svg` where a SVG was posted - a set made without a SVG removes the one the old set had, since it would draw the old picture beside the new icons. Everything is made before the first file is written, so a picture that cannot be used changes nothing; the files are then written one after the other, each beside its place and renamed over it, and a file that cannot be written puts the files already written back. The manifest is the one that is there, with only these things touched: the 192 and 512 icons are added where it names none of that size, `name` and `short_name` take the name of the site (`/project/company/general/name`) where they are empty, and the two colours are written where one was typed. Every other entry of it stays as it is.

The set that is replaced is kept once, in `private/data/favicon-previous/`, and **Undo** (**Rückgängig**) puts it back byte for byte - the vector icon included, and a missing file stays missing - after a question, since the set that stands is not kept by it. The copy is used up by it, and the next write keeps the next one. **Reset to the base set** (**Auf den Satz der Basis zurücksetzen**) writes the files of the installation (`_admin/install/library/base/favicon/`) after a question, removes the vector icon, and is undone the same way; it is offered while the base unit is on the disk. The activity log records *Generate Favicon*, *Undo Favicon* and *Reset Favicon* and nothing of the upload: no file name, no colour.

**The browser cache.** A browser keeps an icon for a long time and a new one under the same address is not fetched again. The base unit's `html-header.tpl` therefore adds `?v=[[/nino/favicon/stamp]]`, the time the set was written, to every address of the set, and names the vector icon through `[[/nino/favicon/svg]]`, which is the whole `<link>` while `public/favicon/favicon.svg` exists and empty otherwise (see [the fills](development.md#textfills)). A new installation has both. A site that was installed earlier keeps its `html-header.tpl` as it is - the base unit is only delivered to new installations - and adds them by hand: `?v=[[/nino/favicon/stamp]]` behind each of the `favicon/...` addresses in its header, and `[[/nino/favicon/svg]]` right behind the `favicon.ico` link, with no space between them. Until then a new set shows as soon as the browser's own cache of the icon runs out.

## An Image Field of an Element Type

An image field of the **Element Types** tab has a width and a height, and the Elements panel cuts every upload to that box, centred. The switch **Fit instead of crop** (**Einpassen statt zuschneiden**) sets the whole picture into the box instead: the longest side takes the box, the proportions stay and nothing is cut, and a picture smaller than the box keeps its own size - it is not scaled up, so the upload says nothing about a size below the target. The box then is the largest size the field stores, which is what logos of different proportions need; `[image]` in a stack writes the width and height of the file it draws, also for a fit picture under a field that lost the switch. The Elements panel then names the box the largest size instead of the target size. A picture the field already holds stays as it is when the switch changes - uploading again replaces it, and removing it deletes it either way. An image field takes its file from the upload alone: a save keeps the name the element holds or empties the field, and any other name is refused. A picture's file is deleted with the picture only where it lies in the folder of the type's own uploads, `images/elements/<type>/`, and no element names it any more.

## With the Keyboard

The first Tab stop of the workbench is a link that skips the rail and lands on the pane. A panel opened from the rail starts at its name; a row that opens a form takes the focus into it, and *Back* returns the focus to the row that was opened. The action bar at the foot of the screen never covers the field that has the focus. The settings menu of the rail - the theme, the language of the interface - closes with Escape and gives the focus back to its button. **Ctrl+S**, or **Cmd+S**, saves the open form (see [Unsaved Input](#unsaved-input)); it does nothing while a save is running or a question is open, and nothing where the screen holds nothing unsaved.

## Recommended Workflow

1. Build the structure under **Element Types** (a tab of Elements), **Text Keys** (Text), **Image Slots** (Images), **Routes** and **Navigations**.
2. Compose the pages by hand or, where the feature is installed, in the Builder; adjust `assets/style.css` where the delivered look is not the one you want, and check the result in the browser - in the [website window](#following-the-website) beside the workbench, which loads it anew after every save.
3. Fill the content under **Elements**, **Text** and **Images**; hand a language over under **Language › Translations**.
4. Check the Dashboard and the two scans for missing definitions.
5. Create the editor accounts under **Users** with the Editor role - add a role on the **User roles** tab where the two are not enough - and test what they see.
6. Check the frontend, every language, the forms and the responsive layout.
7. Commit the project files.

## If Something Does Not Work

| Problem | Check |
|---|---|
| Login locked after several attempts | Wait out the lockout duration (an hour by default), or lift an account's lock under **Users › Login protection**; an address lock is not listed there and still has to expire; the lock is per account and per address. Behind a reverse proxy, set **Config › Reverse proxies in front of this site**, or every visitor shares one address and one lock. |
| A panel or a tab is missing | The account lacks its permission, or its module is not active. |
| Saving fails | The message says why where Nino has a sentence for it (a value out of range, an address already in use, a file over PHP's upload limit). Otherwise: write permissions of the affected file or directory. |
| A login dialog appears over a form | The session ended; log in again and the request is sent on. *Another account is logged in in another tab* means exactly that: reload the page. |
| Template missing in **Routes** | Only existing `templates/page-*.tpl` files are offered. One a panel of the workbench has written (the Builder creates them) is offered the next time Routes is shown, with no reload; one put on the disk by hand is offered after a reload of the page. |
| The browser still shows the old icon after **Favicon › Generate** | The header of the site has to carry the stamp: `?v=[[/nino/favicon/stamp]]` on every address of the set, see [The Favicon Set](#the-favicon-set-a-tab-of-images). A browser tab keeps its icon until the tab is opened anew. |
| Texts or images missing in a scan | Dynamic keys and images are not statically recognizable. A picture a section has as its background, `[section-wrap image="~background"]`, is found as the slot it names, like any other. A slot the scan proposes for a component that names no size has to be given its width and its height before it is made: a slot is never created one pixel wide. |
| A contact form answers visitors with an error and no mail goes out | One address may make the site send mail only so often in an hour: **Config › Mail calls per address**, `/nino/mail/cap`, 5 by default and 0 for none. A call is counted, not a mail, and the mails you send from the workbench count like any other - a site that sends many from a panel needs a higher number. Behind a reverse proxy, set **Config › Reverse proxies in front of this site** first, or every visitor shares one count. |
| Backup list is empty | Backups are switched off, or no authenticated request has happened today. **Back up now** writes the first archive at once. |
| Website broken after **Config** | Restore the last Git state or backup. |
| No developer password works any more | `/_admin/recovery.php` with the recovery password. |
